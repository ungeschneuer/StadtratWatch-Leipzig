= Laufzeitsicht
:icons: font

== Neue Sitzung

. `leipzig-recordings` (täglich) findet die Aufzeichnung, trägt sie ins Manifest ein und öffnet einen Pull Request von `data/leipzig-recordings`.
. `leipzig-votings` (sobald ein neues Manifest auf `main` liegt, sonst wöchentlich) liest die Tafeln, prüft jede Abstimmung, schreibt die Dateien auf `data/leipzig-votings`, legt die Zitatbilder aller veröffentlichten Abstimmungen und die Tafelbilder der Prüffälle in den Release `evidence-<datum>`, öffnet je Sitzung mit Prüffällen ein Issue und hält einen Pull Request nach `main` offen.
. `leipzig-site-data` erzeugt im selben Lauf die Dateien für die Seite.
. Nach dem Merge baut `deploy.yml` die Seite neu.

== Prüfung

. Prüfende öffnen `/review/leipzig/<datum>`, sehen Tafelbild, Video an der Stelle und die fehlgeschlagene Prüfung.
. Jede Entscheidung wird ein Commit in `corrections-<datum>.json` auf `data/leipzig-votings`.
. `leipzig-review-recheck` wendet die Korrekturen an und erzeugt die Seitendaten neu (bei jeder Entscheidung und täglich). Neu erschienene amtliche Ergebnisse und Verlaufsprotokolle holt der ALLRIS-Runner auf dem Server des Betreibers (`minutes-runner/`), weil ALLRIS GitHub Actions nicht antwortet; danach arbeitet der Recheck mit den gespeicherten Dateien.
. Bis zum Merge zeigt die Seite die Abstimmung als „in Prüfung“ mit Link zur Prüfoberfläche und zum Pull Request.

== Mitglieder

`leipzig-members` (täglich) gleicht OParl ab und öffnet bei Änderungen einen Pull Request von `data/leipzig-members`; Mehrdeutigkeiten werden Issues.
